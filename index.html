WEEK 03November 13, 2026Architecture & planning

How Are We Going to Build ExplainQuest?

This week, our focus is figuring out how to turn ExplainQuest from a project idea into an application we can actually build. Now that our responsibilities are more clearly defined, I’m looking at the technical structure from the backend developer’s perspective. The main challenge is making sure the frontend, server-side logic, database, and AI feedback service can work together without becoming difficult to maintain.

Breaking Down the Problem

When a student submits an explanation, several things need to happen in the right order. The application needs to accept and validate the request, identify the associated topic and reference notes, send the appropriate information to the AI service, and return useful feedback. We also want to preserve previous attempts so students can revisit their progress. If one step fails, we need to avoid losing data or creating duplicate records.

Because multiple team members will be working on different parts of the application, unclear data formats or responsibilities could create integration problems later. That makes defining the boundaries between components just as important as writing the code itself.

Proposed Backend Structure

Our proposed stack includes Next.js, TypeScript, Supabase with PostgreSQL, and the OpenAI Responses API. Rather than introducing another backend framework without a reason, I want to investigate how we can use Next.js server-side functionality to handle requests, validation, and communication with our services. The frontend should interact with a consistent server-side interface instead of accessing sensitive services directly.

For the database, I’m thinking about relationships between study topics, explanation attempts, and feedback. An attempt should be associated with the correct topic and user, while feedback should be linked to the attempt that generated it. This is still a planning model, but mapping those relationships early should make it easier to decide what needs to be stored and retrieved.

Making the Plan Testable

Before building more complicated features, I want us to agree on the shape of requests and responses, the validation rules, and what happens when an external service times out or returns an error. We should also document these decisions and break the work into manageable Jira tasks so each team member can see what needs to happen before integration.

My next step is to sketch the complete submission workflow and identify the first backend tasks we can implement and test. The goal this week is not to claim we have a finished system; it’s to create a realistic plan that gives us a foundation for development. From my experience, spending time on the structure early can prevent a lot of unnecessary troubleshooting once everything starts coming together.

WEEK 02November 8, 2026Backend Development

Planning the Backend for ExplainQuest

This week, our team started moving beyond the initial project pitch and into planning how ExplainQuest will actually work. I've officially been assigned as the backend developer, so my focus will be building the logic connecting the frontend, database, and AI feedback system.

Understanding the Problem

One of my biggest concerns is how we're going to handle the flow of information through the application. When a student submits an explanation, the backend needs to validate the request, associate it with the correct study material, communicate with the AI service, and return feedback to the user.

We also need to consider how information gets stored so students can review previous attempts. Another challenge is handling failures, duplicate submissions, and situations where the AI service doesn't respond.

My Approach to the Backend

My initial plan is to break the backend into smaller components with clearly defined responsibilities. The first component will handle incoming requests and validate the submitted information.

From there, the application will retrieve the relevant study material and prepare the information needed to generate feedback. Once feedback is returned, the backend will associate the results with the correct user, topic, and explanation attempt.

I'm also interested in establishing a consistent API structure early in development. Clearly defined endpoints and response formats should make it easier for the frontend and backend to be developed independently.

Our proposed technology stack includes Next.js, TypeScript, Supabase, and the OpenAI Responses API. I'm planning to investigate how these technologies communicate and which responsibilities should remain on the server.

Next Steps

My next goal is to map out the complete request and response process and begin defining the API endpoints we'll need. I also want to establish how we'll handle errors, validate requests, and communicate with the database before implementing more complicated features.

From my previous software development experience, I've learned that getting the underlying structure right early can save a lot of troubleshooting later. My goal is to build a backend that's reliable, organized, and easy for the rest of the team to integrate with.

WEEK 01November 3, 2026Planning & direction

Getting started with ExplainQuest

For this capstone, I’ll be working on ExplainQuest, a learning application built around explaining a topic in your own words. Students provide reference notes, submit an explanation, and receive AI feedback and follow-up questions to help them identify gaps in their understanding.

I expect to work on either backend programming or the database. My exact responsibilities are still being decided. This journal will document the decisions I contribute to, problems I work through, and what I learn as the project develops.

Where I want to contribute

My interest is in how information moves through the application and how it stays organized. A study session involves more than one answer: it can include reference notes, feedback, follow-up questions, and revised explanations. Keeping that history connected will be an important part of the experience.

My initial questions

  • How should topics, explanation attempts, and feedback relate to each other?
  • What should the backend validate before accepting a submission?
  • How can a student return to a previous attempt and understand their progress?
  • What should happen if a feedback request fails or is submitted twice?
Read my next steps

First, I want to confirm my role with the team and review the proposed technology stack. The pitch discussed Next.js, TypeScript, Supabase, and the OpenAI Responses API. Those are the proposed tools; the team still needs to agree on the implementation.

If I take the database role, my first focus will be identifying the records we need, sketching their relationships, and discussing access rules. If I take the backend role, I’ll focus on the submission workflow, validation, and saving results consistently.

For the next journal entry, I plan to include a concrete design or implementation decision, explain why it was made, and describe how I checked it. At this stage, these are plans rather than completed development work.
